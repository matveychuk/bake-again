# Відгуки без акаунта — початок реалізації

## Актуальний стан: короткий дозвіл додано 31.10.2026

Одноразовий дозвіл **120 секунд** реалізовано й перевірено у hosted Supabase.
Дві початкові міграції community та photo admissions тепер застосовані атомарно,
із записом версій. У БД — лише hashes, строки й зв’язок із конкретним внеском та
файлом. Видача/retry не продовжують deadline; atomic claim перед читанням тіла
блокує replay і паралельний запис. Приймання через сервер перевіряє MIME, точний
розмір, SHA-256, строк під час приймання й стан внеску при фіналізації.

Hosted-проба: одночасні uploads **201/409**, replay **409**, неправильний token
**403**, змінений файл **422**, реальне прострочення **UPLOAD_EXPIRED / 410** в
адаптері. Публічний ключ не виконує RPC й не бачить приватної таблиці/фото.
[Протокол, результати та межі](../../docs/architecture/community-photo-admission-2026-10-31.uk.md).

Код: `server/photo-admission.ts`, `photo-upload.ts`, `photo-storage.ts`. Клієнт
не отримує Supabase signed upload URL. Поки це handler factory й server-only RPC;
публічного guest issuer/upload endpoint у сайті та форми немає. До їх підключення
потрібні реальні anti-spam/browser/network gates, стан після втрати
відповіді, moderation/delete/cleanup. Raw object після незавершеної фіналізації
лишається приватним і підлягає наступному cleanup, а не публікації.

Перевірки цього продовження: community **19/19**, Deno auth **1/1**, personal
**55/55**, TypeScript, lint нових модулів і форматування успішні. Попередня
серверна проба нижче збережена як історія.

## Серверна проба перед коротким дозволом — 31.10.2026

Приватний upload і обробка **перевірені у hosted Supabase**, не лише локально.
Створено окремі admin-only Edge Function і приватний bucket `community-photo-probe`.
Реальне фото 1512 × 1008 перекодовано WASM за 883 мс: вебкопія 311 582 B,
мініатюра 37 152 B. Обидві копії оглянуто у Storage. Публічне/anon читання,
підміна upload-шляху й overwrite відхилені; короткий signed download справді
прострочився. Публічний ключ бачить порожній список і не може записувати файли.
[Повний протокол і точні результати](../../docs/architecture/community-photo-probe-2026-10-31.uk.md).

Межі серверної проби — 2 MiB / 4 MP, один кадр JPEG/PNG/WebP. Live-вхід —
опублікований WebP; сирі телефонні JPEG/HEIC не випробувані. Supabase signed
upload має строк 7200 секунд: його не можна видавати гостю як короткий одноразовий
дозвіл. Наступна робота — серверне приймання/обмеження upload, прив’язка до внеску,
модерація й видалення. Гостьові API, recipe UI і community SQL ще не ввімкнені.

Для серверної проби Саша окремо погодила auth лише тестової функції; ключі
залишилися в Supabase. Проба автоматично припиняє приймання admin-команд
01.11.2026 о 01:00 Europe/Madrid. Нових платних сервісів не підключено.

Перевірки після цього продовження: `test:community` 8/8; Deno auth 1/1;
TypeScript та lint нових модулів успішні. Попередні personal/SEO результати нижче
належать першому локальному етапу; повторно в цьому продовженні не запускалися.

Нижче збережено опис **початкового локального етапу до серверної проби**.

Дата: 2026-10-31. Джерело: [план v2](../../docs/strategy/recipe-community-plan-2026-10-27-v2.uk.md).
Саша доручила почати реалізацію 31.10.2026. Виконано локальну частину етапу 0;
це **не запущений модуль** і не завершена проба у production.

## Реалізовано

- `contracts.ts`: обов’язковий приватний email, ім’я 2–60, текст 1–2000 кодових
  точок Unicode; question/result; оцінка 1–5 лише для власного приготування без
  змін. Статус, account ID та версію не можна додати до браузерного запиту.
- `server/submission.ts`: команда для довіреного сервера. Точна версія й конфігурація
  надходять з серверного resolver; resolver канонічних рецептів ще не підключений.
  У тестах використана синтетична `test-v1`, не вигадана фактична версія млинців.
- Приватні HMAC-ключі email і браузерного контексту мають окремі домени. Email
  зберігається для контакту; формат і збіг адреси не підтверджують особу. Не
  прибираємо `+suffix` або крапки. Немає створення акаунта чи прив’язки до нього.
- Власник має випадковий 256-бітний секрет; сервер зберігає лише SHA-256 із
  прив’язкою до operation ID. Браузер має створити й надійно зберегти секрет
  **до першого submit**; ця інтеграція та endpoints керування ще не реалізовані.
- [Міграція](../../supabase/migrations/20261031210000_community_probe.sql) створює
  окрему схему, таблиці contributions/guest_contacts із RLS та серверну RPC.
  `anon` і `authenticated` не можуть читати таблиці або викликати RPC. Навіть
  `service_role` не має прямого читання цих таблиць; RPC працює через SECURITY
  DEFINER з порожнім search_path. Наявні personal/Auth-політики не змінюються.
- Транзакція зберігає текст і контакт разом; retry повертає той самий ID лише за
  збігу capability hash і fingerprint. Зміна даних під тим самим operation ID —
  конфлікт. Секрет, email, fingerprint і текст не входять у відповідь RPC.
- Початковий ліміт — 10 внесків за ковзні 24 години на приватний ключ браузера.
  Retry перевіряється раніше за ліміт. Це не повний антиспам: новий браузер може
  обійти цей контекст. Turnstile, мережевий ліміт і bounded-body endpoint ще потрібні.
- Повторна оцінка того самого email/версії/конфігурації потрапляє в `pending` і
  ніколи не перезаписує попередню. Немає унікальної довічної резервації голосу за
  непідтвердженою адресою. Розв’язання конфлікту потребує модерації або окремого
  підтвердження володіння; поки немає такого шляху, другий голос не публікуємо.
  Розрахунок публічного агрегату й атомарні дії модератора — наступний етап.
- `invitation-policy.ts`: запрошення тільки після нової підтвердженої публікації,
  без replay/повторного показу, з повагою до наявної newsletter-відмови й інших
  діалогів. За недоступного browser storage автоматичне запрошення не показується.
  Це чиста політика; UI ще не підключений, запитів у Brevo вона не робить.

Ці початкові технічні правила реалізовано в межах доручення почати роботу;
це не окреме підтвердження Сашею кожної рекомендації початкового плану.

## Проба фото

`node scripts/community/prepare-photo.mjs SOURCE MIME OUTPUT_DIRECTORY`

Тільки локальний Node: до 10 MiB і 24 млн пікселів, JPEG/PNG/WebP,
один кадр, відповідність MIME фактичному decoder format, повне перекодування,
застосування повороту, без EXIF/XMP. WebP до 1600 × 1600, якість 82;
мініатюра до 480 × 480, якість 78. Анімація, SVG та HEIC не підтримуються.
Оригінал не перезаписується; повторна проба не перезаписує готові копії.
Не імпортувати `sharp` або цей скрипт у Worker.

Реальна локальна проба 31.10:
`media/web-source/media/recipes/banana-fritters/selected/finished-pan-author-v1.jpg`:
439 722 B → 331 262 B вебкопія + 35 776 B мініатюра. Вихід:
`tmp/community-probe-2026-10-31/`. Вебкопію візуально перевірено: їжа й текстура
збережені. Це авторське тестове фото, не реальний читацький відгук.
У Storage файл не завантажувався; телефон і віддалений runtime не перевірені.

## Перевірено

- `npm run test:community`: 6/6. Реальний PostgreSQL engine PGlite: grants, RLS,
  транзакція, retries, відмова чужому capability, приватність відповіді,
  pending-дублі оцінки, quota, atomic rollback і безпечна відмова replay міграції.
- Декодер: MIME mismatch, пошкоджені дані, SVG/HEIC, справжній двокадровий WebP,
  завеликі байти/пікселі, поворот та видалення метаданих.
- `npm run test:personal`: 55/55; `npm run test:seo`: 9/9; `npm run typecheck` — успішно.
- Lint нових `lib/community/` і `scripts/community/` — успішно. Загальний `npm run lint`
  має помилки поза цією зміною: newsletter-form, recipe-confirmation і delivery.test.
- Не перевірено реальну конкурентність окремих з’єднань Supabase. У SQL є впорядковані
  advisory locks на operation/browser/email; локальні запити виконувалися послідовно.

Міграція **не застосована до Supabase**. Немає нових платних сервісів,
production endpoint, завантажень читачів чи змін сторінки рецепта. Build і
390/900/1440 не перевірялися, бо продуктове UI та його імпорти не змінені.

## Початкова контрольна точка (до серверної проби)

1. Вибрати й перевірити обробник зображень у реальному runtime. У поточному
   `wrangler.jsonc` немає Images binding; локальний sharp цього не замінює.
   Новий платний обробник не активувати без погодження витрат.
2. Підготувати staging-only runtime із серверним доступом лише до community RPC,
   перевіреним антиспамом і незмінним idempotency/capability контекстом. Не
   використовувати service key в браузері або personal backend.
3. Пройти справжню пробу: приватний bucket → upload конкретного файла після
   антиспаму → безпечне декодування → приватні WebP → незалежне схвалення фото →
   серверна видача лише схвалених копій. Перевірити expiry, overwrite і видалення.
   Не робити bucket публічним. Signed upload URL сам по собі не вважати одноразовим
   чи достатнім захистом; перевірити його фактичний строк і повторне використання.
4. Розширити NewsletterInvitation у Design Lab за [контрактом](../../design-system/community.uk.md).
   Чинний inline DOI і hosted-форми повторно перевірити для newsletter-мети;
   не використовувати потік лід-магніту. Прямий DOI після відгуку ще не підключений.
5. Публічне читання з явним списком полів, cursor pagination, керування гостем,
   модерація, видалення/експорт, privacy, backup/restore, kill switches і адаптивна
   секція — до ввімкнення пілота. Поки не підключати схему до recipe UI та SEO.
